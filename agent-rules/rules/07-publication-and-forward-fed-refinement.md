# Publish accepted artifacts and preserve next-run inputs

CI preserves candidates, snapshots and full call logs in its run artifact; validated milestone bytes are published under `runs/<run-id>/`. Final multilingual authoring bytes are preserved under immutable `releases/<run-id>/` paths. Formal Access edition allocation remains separate; draft masks keep edition null and no published operational review is invented. Root views can be partial between the five pushes; consult pipeline-status.json and the last complete next-base.json pointer. Preserve native source/model files with JSON manifests. Detect the target repository's existing structure and schema contracts before generating views; avoid gratuitous migrations. Record relative artifact paths, byte hashes, semantic catalog digest, source/index snapshot, base/template commits, methods/rules/prompt hashes, review scope, optional states and limitations.

Use JSON as the structured source of truth. Generate readable Markdown/site views, preserving formal nontechnical terminology and expert links. Pin English/Greek/French identities and their own semantic digests. A branch/latest URL is discovery, not immutable release evidence.

The controller generates a complete website-compatible root at every phase, including
question-only previews before canonical solutions exist. These are deterministic views
of gated records, not newly accepted SF completions. Preserve pending placeholders,
draft/human-review status and unset assessment results. The output owner's pinned
website workflow reads its own repository. Real publications also merge the checked
archive into en/qwen3 and completed language counterparts, preserving archive parents,
explicit phase status and recoverable publication journals. No rejected candidate or
runtime transcript becomes a published solution. Dry/non-publishing runs do not push
website branches.

Preparation and the five publication milestones are separate dependent CI jobs. Persist a sealed checkpoint on success or failure; restore its byte hashes and output Git bundle on the next job/retry. Each milestone has one commit. A pending publication journal identifies its exact parent, commit and artifact bytes; if its push already succeeded, acknowledge that same commit instead of creating another. Dry fixtures use a test branch by default, a dry-run-validated manifest and a dry-run-base.json test pointer; never forward them as accepted knowledge.

Run deterministic structure/completeness/binding/hash checks and source-linked semantic gates before publication. Compare expected target parent commit and serialize publication. Use only the authorized output repository/branch; never push to the template/curated input repository. Do not overwrite accepted snapshots or force-update history. If parent state changed, reconcile with new evidence/lineage rather than bypassing it.

A complete multilingual release requires all declared catalogs/solutions and requested masks. Requested optional reviewers/comparisons must have explicit completion or incomplete status; omitted variants are not requested. An incomplete extension can be reported separately from a completed core run, but do not label that run as passing the extension. Draft archives do not become accepted outputs.

Construct the next base from the accepted catalog, masks, solutions, explanations, glossary, source dependencies, accepted expert corrections and review history. Recheck against current source snapshots; generated text stays separate from authoritative corroboration. Retain stable meaning, regenerate affected dependencies, preserve corrected defects as qualified regression fixtures and maintain old/new mappings.

Advance the content edition only for changed published content. No-change inspections create review events referencing unchanged content. Keep real UTC times, source publication/effective dates, model IDs and catalog ordinals separate. Update/withdraw/supersede source documents with a recorded new snapshot. Do not autonomously rewrite Access or acceptance policy from a generated suggestion.

Feedback concerns **knowledge and artifacts**, not recursive authoring-model training. Student failure does not invalidate supported accepted content or block its use as a later base. Evidence-backed model failures can enter as correction proposals; student weights do not replace the authoring teacher.
